# Native Windows support

The pipeline controller can run from PowerShell using native Windows Python 3.12.
The Dockerfiles still produce Linux containers, so Docker Desktop must be running
in Linux-container mode. A WSL shell is not required; Docker Desktop may itself
use WSL2 or Hyper-V internally.

## Portability changes

- `filelock` replaces the unconditional `fcntl` import. Its native OS locks
  still reject concurrent schedulers and are released after a process exits.
- Windows children are launched in a new process group and stopped by PID tree
  with `taskkill /T /F`, not Unix `os.killpg`. Only that child tree is targeted.
  Ctrl+C and Ctrl+Break are handled by the controller; cancellation is recorded.
- A reader thread streams pipe output so a silent child cannot block the main
  thread from handling an interrupt on Windows. Subprocess/log text uses UTF-8.
- Text snapshot checks tolerate only LF/CRLF differences, including CSV files
  regenerated by pandas. Actual model bytes are still checked exactly. All other
  text changes remain invalid. `.gitattributes` normalizes future checkouts.
- The optional browser verifier uses the same process-management helpers. The
  systemd installer remains Linux-only and reports that explicitly on Windows.

## What CI does and does not verify

The `Native Windows Python and DVC` job runs on a Windows runner with native
Python. It installs the complete application requirements, checks the real DVC
DAG, runs the portable test suite, then runs the real DVC data/training stages
**twice**, including MLflow logging, model packaging, reload and API predictions.
It also verifies the checked-in model on Windows, including reproduced metrics.
`tests/test_service.py` is excluded because its service path tests are specific
to Linux. No other test skips are allowed.

`tests/test_portability.py` tests competing processes, recovery of an OS lock
following a hard kill, stopping a real child/grandchild tree without killing an
unrelated process, and interrupting a silent controller child. That cancellation
test substitutes only the DVC workload, not the actual processes or OS signal.
On Windows it sends Ctrl+Break to the controller's own process group.

The Windows runner does **not** provide the Docker Desktop Linux engine, so this
job does not claim a real Windows Docker deployment. The Linux job retains the
full Docker/Chromium/Firefox/five-minute/systemd checks. An actual end-to-end
Windows Docker Desktop run on the demonstration machine remains a local check.
Windows Task Scheduler, user logout, host reboot and multi-day operation are not
covered. Read the Actions conclusion for the exact commit; test definitions are
not evidence that a run succeeded.

Evidence: `windows-evidence` contains `reports/junit-windows.xml`,
`reports/native/summary.json`, and logs from both real training runs. Full Linux
container evidence remains in `pipeline-evidence`.

## Run

Follow the Windows section of the main README. Install a new Windows venv rather
than reusing one made in WSL/Linux. Activation is optional because the instructions
call `.venv\Scripts\python.exe` directly. Keep the terminal and Docker Desktop
open while the scheduler is running. Ctrl+C stops scheduling; `pipeline.py down`
removes the project's containers after the scheduler has stopped.
